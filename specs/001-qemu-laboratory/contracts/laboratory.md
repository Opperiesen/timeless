# Laboratory CLI and Boot Contract

Run `python3 scripts/qemu_lab.py {preflight|inspect|run}` from the repository root. Optional `--qemu-bin PATH` selects a locally provisioned binary; otherwise use `qemu-system-aarch64` on PATH. `--manifest PATH` selects the committed manifest for testing. `inspect --output PATH` writes the raw generated DTB (an existing output must not be overwritten); `run --image PATH` requires an existing, nonempty image. Every command checks the pinned Python/QEMU versions and availability of `virt-10.0` before acting. Errors go to stderr and return nonzero; preflight returns JSON observed data on stdout. `inspect` returns the output path/digest. `run` starts QEMU but **does not** return boot success merely because the process started; future J1 testing needs a separate serial sentinel and bounded timeout.

Machine arguments: `-machine virt-10.0,dtb-randomness=off`, `-cpu cortex-a53`, `-smp 1`, `-m 256M`, `-accel tcg`, `-nographic`, `-nic none`, `-nodefaults`, `-serial mon:stdio`, `-no-reboot`. `inspect` adds `dumpdtb=PATH` to the machine; `run` adds `-kernel IMAGE`. No network device or hardware acceleration is required.

**Future J1 boot input:** AArch64 raw image with a compatible QEMU direct-Linux-boot header/placement; execution state, DTB pointer in `x0` and serial device discovery must be verified in a bounded J1 experiment before claiming a boot. An arbitrary flat binary is not guaranteed to satisfy QEMU's loader. The architecture-specific stub owns boot ABI handling, the machine port interprets its hardware description, and common kernel code never assumes QEMU's device addresses. J0 supplies no such image and makes no guest-boot claim.
